# CodeForge product audit and first release plan — 2026-09-30

## A. Executive assessment

CodeForge has a plausible Fastify/Next/Prisma foundation, but it is not ready for a coding contest or public launch. Identity routes and public problem reading have implementations. The judge, contest scoring, ratings, authoring, migrations, operations, and end-to-end tests do not. A green worker or CI script can currently mean only `echo` and exit 0. This assessment uses current `apps/` and `packages/` code. At audit start, `README.md` and `SETUP.md:40-95` described older `frontend/` and `backend/` paths, while the ignored local `MASTER_PLAN.md:23-85` proposed future designs. `README.md` has since been updated to describe the current tree.

The first implemented release slice is a **reviewed, fixed-form objective aptitude test**: admin review, publication, candidate discovery, server-timed attempt, saved answers, server grading, and a private result. It deliberately limits tests to one section, MCQ single choice and true/false, with proctoring off. No quiz content is automatically published. Code submissions now fail closed with HTTP 503 until an isolated durable judge exists (`apps/api/src/routes/submissions.ts:7-17`); the problem UI says this explicitly (`apps/web/src/app/problems/[slug]/page.tsx`). A candidate journey needs a PostgreSQL database with the current schema, a reviewed draft, email delivery, and a browser smoke pass before it can be called operational.

## B. Ranked blockers

**Launch critical:** (1) rotate and investigate the historically exposed database credential; (2) reviewed, reproducible schema migrations plus backup/restore; (3) isolated durable judge or leave coding submissions disabled; (4) complete contest scoring/finalization/rating before advertising rated contests; (5) database-backed quiz and identity browser smoke journeys, authoring, publication/retraction; (6) security regression tests for auth, CSRF, access, and concurrent scoring; (7) deployment, monitoring, incident runbooks, and real e2e CI. A narrow **aptitude-only internal pilot** could precede the judge if those identity/quiz/data/ops checks pass and coding contests are not offered.

**Later:** adaptive IRT, plagiarism signals, proctoring after privacy review, special judges, interactive/subtask problems, social discussions, badges, sophisticated recommendations, live sockets, and globally distributed infrastructure.

## C. Target architecture and operating costs

Keep Next web/admin, Fastify API, Prisma/PostgreSQL, and one Redis instance. PostgreSQL is the source of truth for users, content versions, attempts, submissions, contest scores, rating events, and audit logs. Redis/BullMQ is only a delivery mechanism; an outbox row written with the submission/approval transaction is retried into a queue, and workers reconcile orphaned rows. Private S3-compatible object storage holds hidden tests/reference solutions with worker-only credentials; public samples can use a separate bucket/prefix. No API role can download hidden objects.

The judge is a separate worker fleet executing each submission in an ephemeral sandbox with no outbound network, unprivileged user, read-only root filesystem, bounded CPU/wall/memory/output/processes, and per-language images pinned by digest. A trusted worker fetches hidden tests, verifies checksums, runs a versioned checker, stores per-case results, and commits one final verdict under a compare-and-swap state transition. Timeouts, sandbox crashes, and dependency outages yield retryable `JUDGE_FAILURE`, never wrong answer. An outbox reconciler retries stuck jobs and quarantines repeated failures. Custom checkers run with the same isolation and limited private data. Run/submit both use this service; “Run” can use only samples/custom input and may not see hidden outputs.

Contest standings derive from final judged submissions in PostgreSQL, with format-specific scoring policy and deterministic ties. Freeze and finalization are explicit states. A finalization job records a versioned standings snapshot and idempotent `(contest,user)` rating changes in one transaction; a rerun compares source versions and supersedes events with an audit trail. Practice solved count, contest rating, and aptitude score have separate tables and UI labels. Bans exclude public rankings without deleting audit history. Fraud flags or disputes pause publication of affected results until human review.

Deploy web/admin/API as separate services, workers in a restrictive compute pool, managed PostgreSQL with point-in-time recovery, one managed Redis, private object storage, and centralized logs/alerts. Start in one region. Avoid Kubernetes/ClickHouse until throughput requires them. Cost model per month: **fixed** web/API instances + PostgreSQL/backup + Redis + storage/monitoring; **variable** `(submissions × average isolated CPU seconds × worker CPU price)` plus object requests and email. At 10,000 submissions/day and 2 CPU seconds each, judging consumes about 167 CPU hours/month (before image startup/retries); a 10× contest burst needs queue capacity or admission control. The aptitude pilot has negligible compute per response relative to database and mail. Prices must be quoted against the chosen region/provider before budgeting; no provider price is assumed here.

## D. Milestones and acceptance

1. **Internal objective aptitude pilot (implemented code, integration pending):** reviewed draft → publish → register/verify/login → start → answer/reload → deadline/submit → private result. Acceptance: no answer keys in candidate responses, wrong user gets 404, duplicate submit is idempotent, saved answers survive reload, deadline rejects saves, browser test passes with a disposable PostgreSQL instance, and reviewer audit exists. One section, two item types, no proctoring, no percentile.
2. **Database and identity foundation:** baseline migrations against disposable copy, backup/restore, safe seed, token race fixes, admin role provisioning, email delivery and cross-browser auth/CSRF tests. Depends on a disposable DB and mail sandbox. Acceptance: migration deploy/rollback rehearsal and restore with data counts/checksums; concurrent token tests; CI e2e journey.
3. **Practice coding judge:** isolated worker + queue/outbox + storage + checker + run/submit/history UI. Depends on milestone 2. Acceptance: five languages pinned, memory/time/output/network escape tests, hidden test confidentiality, crash/retry/idempotency tests, 1,000 queued submissions recover without duplicate score increments.
4. **Unrated contests:** author/schedule/register, server timing, standings, penalties, freeze/finalize/rejudge/disputes. Depends on judge. Acceptance: deterministic ICPC standings after retries and rejudges, no prestart/late/unregistered submissions, repeat finalization identical.
5. **Rated contests and content operations:** validated rating algorithm/event history, bans/fraud review, full editorial/hint/discussion authoring and moderation, daily reviewed content pipeline. Depends on contest and content versioning. Acceptance: reproducible ratings from event log and human review of every new daily item.

Do not invite external users to coding contests until milestones 2–4 pass. A first externally usable release can be an aptitude pilot only after milestone 1 and the data/identity/ops parts of milestone 2 pass.

## Daily coding and aptitude question pipeline

**Smallest safe daily run:** a scheduled PostgreSQL-backed job chooses one coding topic and one aptitude topic from a reviewer-approved calendar. An ingestion/generation agent may create drafts only. It records prompt/model/version, source URL/license/author, generated text and hashes. A similarity worker checks exact and fuzzy duplicates against the bank and permitted external corpora; a rights reviewer confirms provenance. An independent solver agent prepares a reference answer and explanation. Coding test agents generate samples, edge/adversarial/large cases and run at least two independently authored solutions in the isolated judge; mutation tests must reject known wrong solutions. Aptitude validators independently recompute objective answers and check distractors, ambiguity, timing and accessibility. An automated QA worker computes a quality score, but **only a human reviewer with a distinct account** can approve a specific immutable version. The scheduler publishes that reviewed version at a configured time in one transaction and writes an audit event. Any failure stays draft with a reason and retry budget.

**Agents and permissions:** topic planner reads calendar/performance aggregates; draft generator writes draft content only; provenance scanner reads draft/source metadata; verifier reads draft reference material and uses restricted judge credentials; QA scorer writes reports; reviewer can inspect keys and approve/reject but cannot silently edit approved versions; publisher can publish only signed approvals; monitor reads anonymous post-publication metrics and creates anomaly alerts. Candidate/API credentials read only the public projection. Hidden tests, reference solutions and keys remain in worker/reviewer storage and never appear in candidate JSON or logs.

**Data/queues:** add `ContentVersion(id,kind,parentId,version,status,source,license,promptHash,contentHash,qualityScore,createdBy,approvedBy,approvedAt,publishAt,withdrawnAt,reason)`, `ValidationRun(versionId,toolVersion,checks,artifacts,result)`, `Approval(versionId,reviewerId,decision,notes)`, `PublicationEvent(versionId,action,actorId,at)`, and `AffectedScore(versionId,submissionOrAttemptId,old,new,reason)` with immutable audit records. Queues: `draft`, `verify`, `review-notify`, `publish`, `monitor`, `rejudge`; each has stable job IDs, backoff, retry ceilings and dead-letter visibility. Atomic DB outbox precedes any queue publish. No LLM has publish or production DB write credentials.

**Quality score:** use a 100-point review rubric: correctness independently reproduced (25), provenance/license and duplicate check (20), clarity and unambiguous wording (15), difficulty calibration (15), edge-case tests or aptitude distractor quality (15), and accessibility/formatting (10). Require at least 85, full marks on correctness and provenance, and an independent human approval. Record each component and artifact so a reviewer can dispute the score; the total alone cannot publish content.

**Rollback/rejudge:** withdraw the exact version, hide new attempts, preserve old content and audit, identify every affected submission/attempt by frozen version ID, rerun grading against a reviewed replacement or void the item, recompute dependent contest standings/rating events or aptitude scores, notify affected users, and retain before/after evidence. A human resolves ambiguous or disputed cases. Monitor anomalous acceptance rates, judge failures, comments/reports, and item response curves daily.

**Cost and quality controls:** cap drafts/day, tokens/draft, verifier runs, sandbox CPU, and retries; cache duplicate checks and stop early on provenance failure. Start with one item of each kind per day and one reviewer. Before scheduled publication require 100% independent review; zero candidate key leaks; all reference solutions pass all hidden tests and known incorrect solutions fail; no unresolved license/duplicate flags; and publication/rollback idempotence in repeated-job tests. Monitor 24-hour appeal rate and judge failure rate, with manual withdrawal threshold set before launch.

## E–F. Implementation and verification

Implemented in this working tree: quiz API and candidate pages (`apps/api/src/routes/quiz/index.ts`, `apps/web/src/app/aptitude/`), admin review page (`apps/admin/src/app/admin/quiz-review/page.tsx`), draft seed content (`packages/db/prisma/seed.ts`), verification resend/password recovery screens, CSRF/CORS repair, private problem/contest guards, and closed coding submission route. Existing uncommitted admin/shared/proctor work was preserved. The quiz uses current Prisma models and needs **no new destructive schema command** for this patch; the lack of versioned migrations remains a release blocker.

Verification record: initial `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` all failed because local pnpm attempted to fetch its declared v9.0.0 and network access failed. `turbo lint/test/build/typecheck` then hit pnpm shim/version or subprocess `EPERM`; these are not product passes. Direct `tsc --noEmit` for API/web/admin passed; `prisma validate` and `prisma generate` passed; direct ESLint for API/web/admin passed; direct API `tsc -p tsconfig.build.json` and seed-file typecheck passed. Direct `vitest run --coverage` passed **25/25 across eight API test files** with subprocess permission, including mocked quiz publication → attempt → result, verification resend, refresh replay, CSRF 403/401, production config rejection, and judge 503. Quiz route statement coverage was 92.59%; legacy route coverage is much lower and the PR coverage gate may fail on touched legacy files. Web and admin production builds passed, including the new recovery pages. `git diff --check` passed. A disposable-DB/browser journey remains unrun. Docker is unavailable in this environment; no unknown database was migrated, seeded, or modified.
